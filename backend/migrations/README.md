# Schema migrations

Forward-only, ordered, idempotent SQL. Runner lives in
`backend/app/database.py::run_migrations`.

## Why not Alembic

`alembic==1.14.1` is pinned in `requirements.txt` but was never configured. It
was evaluated and rejected here:

- **The schema's source of truth is raw SQL, not the ORM.** `backend/init.sql`
  is what actually built the live database; `app/models/__init__.py` is a
  hand-maintained mirror of it and `knowledge/calibration.py` talks to the
  database in raw SQL. Alembic's value is `--autogenerate` diffing models
  against the database. Adopting it would make three artefacts that must agree
  (init.sql, the models, the version chain) instead of two.
- **The live volume was hand-patched.** `calibration_records` was created by
  hand because `init.sql` does not re-run. An autogenerated diff against that
  volume cannot be trusted without a manual review of every operation, which is
  the work Alembic was supposed to save.
- **Forward-only is the requirement.** Downgrades, branching and merge points
  are Alembic's differentiators and none of them are wanted. Rolling a
  production schema backwards is not a procedure this project should have.
- **Startup integration is awkward.** The app is fully async; Alembic's runtime
  is sync and needs `run_sync`/greenlet plumbing or a subprocess to run inside
  the FastAPI lifespan.
- **Auditability.** The whole runner is ~120 lines in a file the persistence
  owner already owns, and each migration is SQL a reviewer can paste straight
  into `psql`.

If the schema ever grows to the point of needing branching or downgrades, the
`schema_migrations` ledger maps cleanly onto Alembic's `alembic_version` and the
switch stays open.

## How it works

1. Discovers `backend/migrations/NNNN_lower_snake_name.sql`, sorted by `NNNN`.
2. Creates `schema_migrations (version, name, checksum, applied_at)` if absent.
3. Takes a Postgres advisory lock so two backends starting at once serialise.
4. Applies each unapplied file inside its own transaction, together with the
   ledger insert. Postgres has transactional DDL, so a failed migration leaves
   no partial change and no ledger row.
5. Stops at the first failure — later migrations may depend on the failed one.
6. Re-running is a no-op. If an *already applied* file's checksum has changed,
   it logs an error and reports it rather than re-applying: applied migrations
   are immutable, ship a new one instead.

`run_migrations()` never raises. It returns
`{"applied": [...], "skipped": [...], "errors": [...], "ok": bool}` so that
calling it from startup cannot take the service down.

## Running them

Single documented command:

```bash
docker compose exec backend python -m app.database
```

Exit status is 0 when `ok`, 1 otherwise. Output:

```
applied=['0002'] skipped=['0001'] errors=[]
```

To run automatically at boot, `app/main.py`'s lifespan needs three lines (see
the persistence agent's report — `main.py` is not owned by `agent/persistence`):

```python
from app.database import run_migrations
result = await run_migrations()
if not result["ok"]:
    logger.error("Schema migrations reported errors: %s", result["errors"])
```

## Keeping `init.sql` and migrations in sync

`init.sql` is a **fresh-volume fast path only**. The migrations are
authoritative and run on every volume, fresh or not.

The guarantee comes from making every migration idempotent
(`ADD COLUMN IF NOT EXISTS`, `CREATE TABLE IF NOT EXISTS`, guarded `DO` blocks).
That means:

- On a fresh volume, `init.sql` creates the object and the migration is a no-op.
- On the live volume, `init.sql` never ran, and the migration creates the object.
- If someone forgets to update `init.sql`, the migration still converges the
  fresh volume to the right schema. The two paths cannot diverge in a way that
  matters.

Rules for adding a schema change:

1. Add it to `init.sql` **and** as a new numbered migration, in the same commit.
2. The migration must be idempotent. A migration that would fail when the
   object already exists breaks the fresh-volume path.
3. Never edit an applied migration — the checksum check will flag it.
4. Update `app/models/__init__.py` in the same commit if the ORM covers the
   table.

## Deploy note

`docker-compose.yml` bind-mounts `./backend/app:/app/app` only, so this
directory is baked into the image at build time. A deploy that adds a migration
needs `docker compose up -d --build backend`, not just `git pull`. Adding
`- ./backend/migrations:/app/migrations` to the backend service would remove
that requirement; `docker-compose.yml` is owned by `agent/devops`.
